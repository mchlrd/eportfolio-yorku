## Artifact 01 — Isolated malware analysis lab

work sample · cloud security · 2026

Design Use of Engineering Tools Investigation Impact on Society and the Environment

Introduction

Suspicious files needed to be executed and studied without any path back to production. I designed and secured an isolated analysis environment in AWS — EC2 instances inside dedicated VPCs, private subnets, security groups, IAM integrations, and S3 buckets — so that artifacts could detonate and be analysed with confidence that the blast radius was contained. What it demonstrates: designing for containment under real constraints rather than building the happy path and hoping.

reflection

Retell — what I created or did

Analysing potentially harmful artifacts means running them, and doing that anywhere near live infrastructure is negligent. So the first problem was not analysis at all — it was creating somewhere safe enough for analysis to be permitted. I built that environment, then worked through artifacts using PEStudio, Detect It Easy, FakeNet-NG, HxD, and Sysinternals, applying static reverse-engineering techniques to describe malicious behaviour and extract indicators of compromise.

Relate — how this connects to my goals

The engineering design cycle I have studied — define the need, establish constraints, generate and evaluate alternatives, implement — mapped onto this problem more cleanly than anything I had built before. The decisive constraint was not technical capability but consequence: the design had to fail safely, because the material was designed to cause harm. That is inseparable from the ethics work in Goal 3, and it is the reason containment mattered at all.

Reflect — what I learned

What I learned about myself is that I default to solving the immediate problem and treating constraints as somebody else's job. My first instinct was to pick the analysis tools; the actual engineering question was the boundary condition. What changed my thinking was realising that the isolation was the deliverable — a brilliant finding produced in an unsafe environment would have been worthless and irresponsible. What I would do differently is write the containment argument down first and let it dictate the tooling, rather than choosing tools and retrofitting a boundary.

Competency

Design — a solution engineered to satisfy competing constraints, analytical capability against strict containment. Use of Engineering Tools — EC2, VPC, IAM, PEStudio, FakeNet-NG and HxD selected and operated to serve a defined objective rather than used for their own sake.

## Artifact 02 — Vulnerability remediation automation

work sample · automation & security operations · 2026

Problem Analysis Use of Engineering Tools Life-Long Learning Professionalism

Introduction

Responding to CISA's Known Exploited Vulnerabilities catalogue was a manual, repetitive, easily deprioritised process. I developed Python and PowerShell automation using Microsoft Graph, the Azure SDK, REST APIs, and regex parsing to drive KEV remediation, endpoint reporting, and vulnerability validation. What it demonstrates: recognising that the bottleneck in security operations is usually process, not tooling.

reflection

Retell — what I created or did

Every week brought a new list of known-exploited vulnerabilities and a queue of endpoints to check against it. Handled manually the work was slow and, worse, invisible — nobody could see coverage until someone asked. I wrote automation that queried the relevant Microsoft APIs, parsed and matched results, generated reporting, and validated remediation status, with scheduled Function Apps and notification workflows so the pipeline ran and reported without being driven.

Relate — how this connects to my goals

This is the problem-analysis approach central to engineering: state the problem before reaching for a solution. The stated problem — "we have vulnerabilities to remediate" — was misleading. The real problem was that remediation depended on a person remembering to do it, which meant the process failed silently whenever workload spiked. Reframing it changed what a solution even looked like. It also sits directly in Goal 2, where the skill is building automation that holds up.

Reflect — what I learned

What I learned about myself is that I am willing to do repetitive work patiently — which sounds virtuous and is actually a trap, because the patience delayed me from questioning whether the work should exist. What changed my thinking was measuring the manual process and realising how much of a security team's week was being absorbed by tasks a script could do better and never forget. Since then I try to ask "should this be automatic?" before "how do I do this faster?". What I would do differently is instrument the automation from the start: a process that cannot report its own coverage is only marginally better than a manual one nobody can see.

Competency

Problem Analysis — reframing a staffing problem as a process problem and then an automation problem. Use of Engineering Tools — Graph, the Azure SDK, REST APIs and regex parsing applied deliberately, each chosen for a specific part of the workflow and documented so it could be maintained by someone else.

## Artifact 03 — Quantifying technical risk

work sample · risk & economics · 2026

Economics and Project Management Problem Analysis Communication Skills Investigation

Introduction

A proposed expansion into SaaS and lead-generation markets hinged on infrastructure that had never been stress-tested against it. Applying the FAIR framework, I quantified financial and operational exposure — Asset Value, Exposure Factors, Single Loss Expectancy, Annualized Loss Expectancy — and used exponential failure models to calculate MTBF, producing a probability and impact picture leadership could actually decide against. What it demonstrates: translating gut-feel risk into numbers somebody can argue with.

reflection

Retell — what I created or did

The team wanted to know whether the existing infrastructure could support a significant expansion without degrading, and "probably" was not a sufficient answer for a decision that size. I modelled the financial exposure of a potential breach using FAIR, calculated reliability metrics including MTBF using exponential failure distributions, and ran threat-modelling SWOT assessments to convert ambiguous market conditions into structured findings. The output was a co-authored, employer-facing strategy report.

Relate — how this connects to my goals

This is the economics competency in a form I had not expected to meet as a security-minded student: the same technical facts, expressed as money and downtime, became a decision instead of an opinion. It also reinforced something I have had to relearn more than once — that communication is not polish, it is the delivery mechanism for the analysis. An unpresentable risk model helps nobody, which is why goal 3 of my Personal Development Goals targets exactly this weakness.

Reflect — what I learned

What I learned about myself is that I am more comfortable producing an analysis than defending one, and that the discomfort is worth pushing through. Presenting range-based estimates to people who wanted a single number taught me that intellectual honesty often looks like unhelpful hedging until you explain why the range is the answer. What I would do differently is build the probability and impact matrix with the audience in mind from the first day rather than translating it at the end — the framing that finally made it land should have shaped the analysis from the start.

Competency

Economics and Project Management — expressing technical risk in financial and reliability terms that supported a genuine business decision. Problem Analysis — converting an ambiguous question into defined variables with stated assumptions that could be challenged and revised.

## Artifact 04 — Deployment automation

work sample · systems & embedded · 2024

Use of Engineering Tools Individual and Teamwork Knowledge Base for Engineering Design

Introduction

Hardware staging was slow, inconsistent, and hard to hand over. I designed and optimised Linux-based workflows with Shell, C, and Python automation, prototyped ESP32-C3 microcontrollers for automated diagnostics and testing, and built Windows configuration pipelines that ingested Registry values programmatically to enforce baselines consistently. What it demonstrates: my first measured experience of automation changing how a team spends its day.

reflection

Retell — what I created or did

Getting hardware ready involved a manual sequence repeated for every unit — slow, and prone to drifting between whoever ran it. I wrote automation in Shell, C, and Python that reduced deployment time by 20–35% while making the process reproducible, then extended it into embedded work: programming ESP32-C3 boards to run automated diagnostics and tests. On the Windows side I built configuration pipelines that wrote Registry values programmatically, so security baselines were applied identically every time instead of being remembered correctly by a person.

Relate — how this connects to my goals

This is where the knowledge-base competency stopped being theory and started being a tool: low-level systems knowledge is what made it possible to automate below the operating system, and the scripting was the easy part once the underlying behaviour was understood. It also connects to teamwork in a way I had not anticipated — the value of the automation was not mine, it was the team's, and it only counted once somebody else could run it without me present.

Reflect — what I learned

What I learned about myself is that I am motivated by the moment a process stops being painful for somebody else — that is the feedback loop that keeps me going, more than solving the puzzle did. What changed my thinking was realising that a script only I understood was a single point of failure with good intentions. What I would do differently is write the usage notes first and treat documentation as part of the deliverable rather than a courtesy added afterwards if there is time.

Competency

Use of Engineering Tools — scripting and embedded toolchains applied to a measurable operational problem, a 20–35% reduction in deployment time. Individual and Teamwork — the deliverable was designed to be handed over and run by others rather than kept as personal output.

## Artifact 05 — Handling malicious software, and who carries the risk

ethics & sustainability discussion · 2026

Ethics and Equity Impact on Society and the Environment Professionalism

Introduction

An artifact that is a discussion rather than a build. During my placement I handled material designed to cause harm — executing suspicious files in an isolated environment, and working with highly restricted intelligence alongside federal cyber-security partners. Neither task raised a technical problem I could not solve. Both raised questions I had not been asked to think about: who is exposed when this work goes wrong, who benefits from it, and what the environmental cost of the infrastructure behind it actually is.

reflection

Retell — what I created or did

I built and operated an isolated cloud environment for analysing malicious software, and I took part in incident investigations involving restricted federal intelligence. In both cases the material was sensitive, the surrounding process was strict, and the purpose was protective: understanding an attack so that it could be detected or stopped elsewhere. On the environmental side, analysis environments like the one I built consume real compute — instances, storage, and network capacity that run whether or not anyone is actively using them.

Relate — how this connects to my goals

The ethics material asks who is affected by a technical decision, including people who never agreed to be part of it. In this work the people affected are residents of a county who will never know an incident happened, and in the federal case, members of the public whose safety depends on intelligence being handled correctly. The sustainability question follows the same logic one step further out: every analysis environment that is left running has a cost paid by someone else, in energy and resources. Designing for containment also means designing for disposal, and treating an idle instance as free is exactly the kind of unexamined assumption this goal is meant to expose.

Reflect — what I learned

What changed my thinking was noticing that "it is isolated, so it is fine" is not an ethics position — it is a technical answer to a non-technical question. Isolation protects the systems, but it says nothing about whether the work should be done, who authorised it, or what happens to the people on the other end of the analysis. What I learned about myself is that I default to the engineering frame and find the accountability frame easy to skip, which is precisely the failure mode the competency is warning about. What I would do differently is ask the second question explicitly at the start — not only "can this be contained?" but "who bears the risk if it is not, and have they agreed to it?" I do not think my work was wrong. I do think I reached that conclusion by assumption rather than by reasoning, and that is worth correcting.

Competency

Ethics and Equity — the artifact reasons about who is affected by protective security work, including people with no part in the decision, and about the limits of a purely technical justification. Impact on Society and the Environment — it extends that reasoning to the resource cost of the infrastructure itself, treating an idle analysis environment as an ongoing claim on shared resources rather than a neutral choice.

## Independent projects

The five artifacts above come from placements or paid work. The four below were built on my own time, from an empty subscription or a bare hypervisor, with nobody specifying the requirements but me. They are the clearest evidence I have of self-directed work, and they are all public on GitHub.

### Artifact 06 — Azure Cloud SOC lab

independent project · cloud detection engineering · source ↗

Design Use of Engineering Tools Investigation

Introduction

A cloud-native Security Operations Centre built from scratch in Azure: a Windows Server 2025 target running Sysmon, Azure Monitor Agent shipping Windows Security and Sysmon logs through a Data Collection Rule into a Log Analytics workspace, and Microsoft Sentinel on top for detection and dashboards. I then attacked my own environment — RDP brute-force attempts and Nmap scans — and wrote KQL to find what I had done. What it demonstrates: building the telemetry pipeline before the detections, rather than the other way round.

reflection

Retell — what I created or did

I built the whole chain rather than operating one. Resource group, Log Analytics workspace, a target VM with Sysmon installed, the Azure Monitor Agent wired up through a Data Collection Rule so that Windows Security events and Sysmon operational logs actually landed somewhere queryable, then Sentinel as the layer on top. Only once logs were flowing did I generate traffic: repeated failed RDP logons to produce Event ID 4625, and port scans to produce Sysmon Event ID 3 network connections. Then I wrote the analytics rules and dashboards that would have caught it.

Relate — how this connects to my goals

This is the design competency in its least visible form. The design decision was not the dashboard — it was what telemetry to collect, at what granularity, and where to keep it, because that decision determines everything you can ever detect afterwards. Getting it wrong is silent. It also connects directly to Goal 2: the placement taught me to operate a detection stack, and this was my attempt to build one where I had made every choice myself.

Reflect — what I learned

What I learned is how many decisions were already made for me in a working environment. Collection scope, retention, what counts as normal for a given host — all of that was inherited, and I had never noticed it. The uncomfortable part is that my first detections were written knowing exactly what the attack looked like, which means I was tuning to a test I had designed. That is not the same skill as detecting something unfamiliar, and I should not confuse the two when I describe this work. What I would do differently is establish a baseline before attacking — run the environment normally for a while, record what ordinary activity looks like, and build detections against that, so they have a reference point rather than a target.

Competency

Design — the telemetry architecture is the design, and it was chosen deliberately to support detections that did not exist yet. Use of Engineering Tools — Azure Monitor, Data Collection Rules, Sentinel, Sysmon and KQL each configured and used for a specific job. Investigation — validating that the pipeline carried real evidence by reproducing attacks and confirming what surfaced.

### Artifact 07 — Suricata & Splunk SOC lab

independent project · network intrusion detection · source ↗

Use of Engineering Tools Investigation Knowledge Base for Engineering

Introduction

A self-contained network monitoring lab: Kali Linux as the attacker, a Windows victim, Suricata IDS inspecting the traffic, and Splunk Enterprise ingesting the alerts into real-time dashboards. I wrote custom Suricata rules for reconnaissance behaviour — ICMP sweeps, TCP SYN scans, Nmap scans, and both NULL and FIN scans — and built SPL queries to visualise alert distribution and top source IPs. What it demonstrates: writing detection logic means understanding what an attack actually looks like on the wire.

reflection

Retell — what I created or did

I segmented a virtualised network so the attacker and victim lived on an isolated subnet, then set Suricata inspecting the interface with a local rules file I wrote myself. The rules were the real work: a SYN-scan signature, an Nmap signature, a threshold rule for repeated connection attempts from one source, and separate rules for NULL and FIN scans. Splunk monitored the alert log as a file input under a custom sourcetype, and I built a timechart of alerts by message and a pie chart of alert distribution against it.

Relate — how this connects to my goals

This is where the knowledge-base competency became concrete rather than theoretical. A SYN scan, a NULL scan and a FIN scan are three different exploitation of the same TCP handshake, and they produce three different packet signatures — which means a rule that catches one can miss the others entirely. Writing the rules forced me to understand the protocol at the level of flags, not descriptions. It sits under Goal 2 as the network half of the detection work I want to specialise in.

Reflect — what I learned

What changed my thinking is the realisation that detection coverage is not a shield — it is a set of blind spots you have mapped. Running my own rules against my own scans made that concrete: they caught everything, because I wrote them after choosing the attacks. A rule that passes its test tells you almost nothing about a rule that has never met an adversary. What I would do differently is attack the detection instead of confirming it: run a deliberately slow, fragmented or obfuscated scan against my own signatures to find where they fail, and treat the failures as the actual deliverable. I also learned that a lab has real resource costs — the multiple VMs and a full SIEM need serious hardware, which is a genuine engineering constraint and not just an inconvenience.

Competency

Use of Engineering Tools — Suricata rule syntax, Splunk search processing language, and virtualised network configuration, each used to produce a specific analytical result. Investigation — correlating alerts across two tools to separate confirmed reconnaissance from ordinary background traffic.

### Artifact 08 — pfSense network security lab

independent project · network segmentation & policy · source ↗

Design Investigation Professionalism

Introduction

A controlled lab evaluating how a stateful firewall actually behaves rather than how it is described: pfSense as a Layer 3 gateway with session tracking, internal clients and target hosts, and deliberate service enumeration across SMB, RDP, RPC, NetBIOS and HTTP/HTTPS. Scan results were cross-referenced against firewall logs to distinguish open, closed and filtered states, and to test how rule ordering changes what is reachable. What it demonstrates: that policy is defined by rule order, and that the log is the only proof of what the policy really is.

reflection

Retell — what I created or did

I placed a firewall between internal hosts and inspected everything crossing it, then tried to break my own rules. I checked stateful behaviour properly — confirming it tracked sessions, separated new connections from established ones, and logged pass, block and drop distinctly — then scanned across the high-risk ports and compared what the scanner reported against what the log recorded. The rule-order tests were the most revealing part: deliberately moving and reordering rules to see whether the policy I had intended was the policy that was enforced.

Relate — how this connects to my goals

This is the lab that most directly reinforced my placement work, where I administered Cisco Meraki MX firewall rules, VPN policies and security event logging. Doing the same job on pfSense — where I had to build the topology myself instead of inheriting one — clarified what those Meraki rules were actually doing and why their order was not arbitrary. It also made the distinction between a filtered and a closed port concrete, which is a difference that matters when you are reading a scan result and deciding whether a service is safe.

Reflect — what I learned

What changed my thinking is that rule order matters more than rule content. A rule can be perfectly written, correctly scoped and completely inert because of what sits above it, and nothing about the rule list tells you that. I understood this properly only after watching traffic succeed to a port I believed was blocked, and having to explain why to myself. Since then I am careful with the sentence "the firewall blocks that" — it is a claim about an ordering, and the only evidence for it is the log. What I would do differently is write the intended policy matrix first — what is allowed to talk to what, on which port, in which direction — then implement it, then verify against it. I built rules first and inferred my own intent afterwards, which is backwards and is the mistake the lab was expensive enough to teach me.

Competency

Design — segmentation and rule structure chosen to express an intended policy under real constraints. Investigation — treating firewall logs as the primary source of evidence and using them to validate or falsify what the rules were supposed to do. Professionalism — the lab was documented throughout with screenshots and a written record, because an undocumented configuration cannot be verified by anyone else.

### Artifact 09 — Flight price prediction

independent project · machine learning · source ↗

Knowledge Base for Engineering Problem Analysis Investigation

Introduction

The one artifact here that is not security work, and the reason it is included is that its most useful outcome was a lesson about measurement rather than about models. I built a regression pipeline in Python that predicts airline ticket prices from flight attributes — carrier, route, timings, stops, class, duration and days until departure — using a Random Forest Regressor with GridSearchCV and RandomizedSearchCV for hyperparameter tuning, evaluated on R², MAE, MSE and RMSE.

reflection

Retell — what I created or did

I cleaned the dataset, dropped the columns that carried no signal, encoded the categorical features with dummy variables and label encoding, and split the data 80/20. I trained a Random Forest Regressor, then spent a substantial amount of time running GridSearchCV and RandomizedSearchCV to find better hyperparameters, and visualised predicted against actual prices along with feature importance. The final model reported an R² of 0.979.

Relate — how this connects to my goals

This connects to the knowledge-base competency and, unexpectedly, to the way I now approach detection work. Evaluating a model is structurally the same problem as evaluating a detection: you are asking whether a strong-looking number actually means what you want it to mean. It also gives me a second discipline to draw on — the automation and analysis I do in security increasingly involves statistical reasoning, and this was the project where I learned how easy it is to be misled by a metric.

Reflect — what I learned

What changed my thinking was learning what R² does not tell you. An R² of 0.979 reads as a clear success, and with hindsight I treat it as a warning instead: the dataset is a clean, simplified one in which price is largely a function of the attributes provided, so a flexible model can recover something close to a deterministic relationship. That is fitting, not forecasting. I did not distinguish those two things at the time, and I presented the score as evidence of a good model. What I would do differently is interrogate the data before tuning anything: ask whether the target is derivable from the features, look deliberately for leakage, and hold out something the model genuinely cannot already know. The hyperparameter search was the most enjoyable part of the project and probably the least important — the consequential decision was dataset selection, which I gave almost no thought to.

Competency

Knowledge Base for Engineering — regression, feature encoding and model evaluation applied end to end in Python. Problem Analysis — framing a prediction task and then having to reconsider whether the framing itself was sound. Investigation — the discipline of questioning a result that looked good rather than accepting it, which is the part of this project I would defend.
