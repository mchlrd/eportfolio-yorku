Artifact 01

Isolated malware analysis lab.

Work sample · Cloud security · 2026

An AWS environment built to be safely broken

Introduction. Suspicious files needed to be executed and studied without any path back to production. I designed and secured an isolated analysis environment in AWS — EC2 instances inside dedicated VPCs, private subnets, security groups, IAM integrations, and S3 buckets — so that artifacts could detonate and be analysed with confidence that the blast radius was contained. What it demonstrates: designing for containment under real constraints, rather than building the happy path and hoping.

Design Use of Engineering Tools Investigation Impact on Society & the Environment
Retell
Analysing potentially harmful artifacts means running them. Doing that anywhere near live infrastructure is negligent, so the first problem wasn't analysis at all — it was creating somewhere safe enough for analysis to be allowed. I built an isolated environment in AWS: EC2 instances inside private subnets, tightly scoped security groups, dedicated IAM roles, and S3 storage for captured evidence, all separated from anything production-facing. Inside it, I worked through artifacts using PEStudio, Detect It Easy, FakeNet-NG, HxD, and Sysinternals, applying static reverse-engineering techniques to describe malicious behaviour and extract indicators of compromise.
Relate
The engineering-design cycle I've studied in coursework — define the need, establish constraints, generate and evaluate alternatives, then implement — mapped onto this problem more cleanly than any assignment has. The decisive constraint wasn't technical capability but consequence: the design had to fail safely, because the material being handled was designed to cause harm. That's the Design competency in its honest form, and it's inseparable from Impact on Society & the Environment — the reason containment mattered was the downstream effect on real infrastructure and real people, not an abstract best practice.
Reflect
What I learned about myself is that I default to solving the immediate problem and treating the constraints as somebody else's job. My first instinct was to pick the analysis tools; the actual engineering question was the boundary condition. What changed my thinking was realising that the isolation was the deliverable — the analysis was only possible because of it, and a brilliant finding produced in an unsafe environment would have been worthless and irresponsible. What I'd do differently is write the containment argument down first and let it dictate the tooling, rather than choosing tools and retrofitting a boundary around them.
Competency justification This artifact demonstrates Design because it shows a solution engineered to satisfy competing constraints — analytical capability against strict containment — and Use of Engineering Tools because the tools (EC2, VPC, IAM, PEStudio, FakeNet-NG, HxD) were selected and operated to serve a defined analytical objective rather than used for their own sake.
Artifact 02

Vulnerability remediation automation.

Work sample · Automation & security operations · 2026

Turning ticket-by-ticket remediation into a pipeline

Introduction. Responding to CISA's Known Exploited Vulnerabilities catalogue was a manual, repetitive, and easily-deprioritised process. I developed Python and PowerShell automation using Microsoft Graph, the Azure SDK, REST APIs, and regex-based parsing to drive KEV remediation, endpoint reporting, and vulnerability validation — so the routine work ran itself and human attention went to the exceptions. What it demonstrates: recognising that the bottleneck in security operations is often process, not tooling.

Problem Analysis Use of Engineering Tools Life-Long Learning Professionalism
Retell
Every week brought a new list of known-exploited vulnerabilities and a queue of endpoints to check against it. Handled manually, the work was slow and — worse — invisible: nobody could see coverage until someone asked. I wrote automation that queried the relevant Microsoft APIs, parsed and matched results, generated reporting, and validated remediation status, together with scheduled Function Apps and notification workflows so that the pipeline ran and reported without being driven. Where identity was involved, I administered Active Directory and Entra ID — users, groups, organisational units, RBAC, Conditional Access, MFA, Intune, MDM, and BYOD policy.
Relate
This connects directly to the problem-analysis approach the course frames as central to engineering: state the problem before reaching for a solution. The stated problem ("we have vulnerabilities to remediate") was misleading — the real problem was that remediation depended on a person remembering to do it, which meant the process failed silently whenever workload spiked. Reframing it as an automation problem changed what a solution even looked like. It also sits squarely in Use of Engineering Tools, where the skill isn't knowing a tool exists but choosing between Graph, the Azure SDK, and direct REST calls based on what the task actually required.
Reflect
What I learned about myself is that I'm willing to do repetitive work patiently, which sounds virtuous and is actually a trap — the patience delayed me from questioning whether the work should exist. What changed my thinking was measuring the manual process and realising how much of a security team's week was being absorbed by tasks a script could do better and never forget. Since then I try to ask "should this be automatic?" before asking "how do I do this faster?". What I'd do differently next time is instrument the automation from the start: an automated process that can't report its own coverage is only marginally better than a manual one nobody can see.
Competency justification This artifact demonstrates Problem Analysis by reframing a staffing problem as a process problem and then as an automation problem, and Use of Engineering Tools by applying Graph, the Azure SDK, REST APIs, and regex parsing deliberately — each chosen for a specific part of the workflow and documented so it could be maintained by someone else.
Artifact 03

Quantifying technical risk.

Work sample · Risk & economics · 2026

Costing a growth strategy before committing to it

Introduction. A proposed expansion into SaaS and lead-generation markets hinged on infrastructure that had never been stress-tested against it. Applying the FAIR framework, I quantified financial and operational exposure — Asset Value, Exposure Factors, Single Loss Expectancy, and Annualized Loss Expectancy — and used exponential failure models to calculate MTBF, producing a probability/impact picture that leadership could actually decide against. What it demonstrates: translating gut-feel risk into numbers someone can argue with.

Economics & Project Management Problem Analysis Communication Skills Investigation
Retell
The team wanted to know whether the existing infrastructure could support a significant expansion without degrading. "Probably" wasn't a sufficient answer for a decision of that size. I modelled the financial exposure of a potential breach using the FAIR framework — asset value, exposure factors, single loss expectancy, annualized loss expectancy — calculated reliability metrics including MTBF using exponential failure distributions, and ran threat-modelling SWOT assessments to convert ambiguous market conditions into structured findings. The output was a co-authored, employer-facing strategy report setting out the exposures and the recommendations for reducing them.
Relate
This is the Economics & Project Management competency in a form I hadn't expected to encounter as a security-minded student: the same technical facts, expressed as money and downtime, became a decision instead of an opinion. The course's emphasis on communicating to an audience is what made the difference — the modelling was only valuable because the report was written for the people who had to act on it, not for people who shared our vocabulary. It reinforced that Communication Skills in engineering isn't polish, it's the delivery mechanism for the analysis itself.
Reflect
What I learned about myself is that I'm more comfortable producing an analysis than defending one, and that the discomfort is worth pushing through. Presenting range-based estimates to people who wanted a single number taught me that intellectual honesty often looks like unhelpful hedging until you explain why the range is the answer. What I'd do differently is build the probability/impact matrix with the audience in mind from the first day, rather than translating it at the end — the framing that finally made it land should have shaped the analysis from the start.
Competency justification This artifact demonstrates Economics & Project Management by expressing technical risk in financial and reliability terms that supported a genuine business decision, and Problem Analysis by converting an ambiguous question into defined variables with stated assumptions that could be challenged and revised.
Artifact 04

Deployment automation.

Work sample · Systems & embedded · 2024

Cutting hardware deployment time by 20–35%

Introduction. Hardware staging was slow, inconsistent, and hard to hand over. I designed and optimised Linux-based workflows with Shell, C, and Python automation, prototyped ESP32-C3 microcontrollers in C and Python for automated diagnostics and testing, and built Windows configuration pipelines that ingested Registry values programmatically to enforce baselines consistently. What it demonstrates: my first measured experience of automation changing how a team spends its day.

Use of Engineering Tools Individual & Teamwork Knowledge Base for Engineering Design
Retell
Getting hardware ready involved a manual sequence repeated for every unit — slow, and prone to drifting between whoever ran it. I wrote automation scripts in Shell, C, and Python that reduced deployment time by 20–35% while making the process reproducible, then extended it into embedded work: programming ESP32-C3 boards in C and Python to run automated diagnostics and tests. On the Windows side, I built configuration pipelines that wrote Registry values programmatically so that security baselines were applied identically every time instead of being remembered correctly by a person.
Relate
This is where the Knowledge Base for Engineering competency stopped being coursework and started being a tool: low-level systems knowledge is what made it possible to automate below the level of the operating system, and the scripting was the easy part once the underlying behaviour was understood. It also connects to Individual & Teamwork in a way I hadn't anticipated — the value of the automation wasn't mine, it was the team's, and it only counted once someone else could run it without me present.
Reflect
What I learned about myself is that I'm motivated by the moment a process stops being painful for someone else — that's the feedback loop that sustains me, more than solving the puzzle did. What changed my thinking was realising that a script only I understood was a single point of failure with good intentions. What I'd do differently is write the usage notes first and treat documentation as part of the deliverable, not a courtesy added afterwards if there's time.
Competency justification This artifact demonstrates Use of Engineering Tools by applying scripting and embedded toolchains to a measurable operational problem (a 20–35% reduction in deployment time), and Individual & Teamwork because the deliverable was designed to be handed over and run by others rather than kept as personal output.
